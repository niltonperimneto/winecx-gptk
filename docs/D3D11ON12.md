# D3D11On12 on D3DMetal

## Status

This document describes the design and implementation status of D3D11On12 in
`relay12`. The implementation is experimental and is not yet capable of
returning a functional D3D11On12 device.

The current code establishes a safe routing and versioning boundary. It must
continue returning `DXGI_ERROR_UNSUPPORTED` until it can return genuine D3D11
interfaces backed by the caller's D3D12 device and command queue.

The clean-room DDI declarations have started: the adapter, resource, device,
core-layer and cache-session handles, both adapter function tables with
`D3D10DDIARG_OPENADAPTER`, the version negotiation arithmetic,
`D3D10DDIARG_CREATEDEVICE` with its embedded DXGI base arguments, the 47-slot
`D3DWDDM2_6DDI_CORELAYER_DEVICECALLBACKS` table, and the 66-slot
`D3DDDI_DEVICECALLBACKS` table with the argument structures its promoted slots
take are authored, asserted, and checked against real objects in both C and
C++. `D3D10DDIARG_CREATEDEVICE` therefore has no unauthored member left, and
both tables the host itself has to fill are declared. What remains is the
tables the driver fills. That is the groundwork for the DDI host, not the
host, and none of it is reachable from the public entry point yet.

`docs/CLEANROOM-DDI.md` is the working guide for the rest of that effort: the
target DDI version and why, the two documentation surfaces and the rule that
they must agree, the order the remaining groups land in, and the measured
sizes behind those estimates.

## Objective

Support Windows applications that call `D3D11On12CreateDevice` while using
Apple D3DMetal as the D3D12 implementation:

```text
Windows application
    -> d3d11.dll router
    -> Wine D3D11 runtime/DDI host
    -> Microsoft D3D11On12 DDI
    -> Microsoft D3D12TranslationLayer
    -> caller's D3DMetal ID3D12Device and direct command queue
    -> D3DMetal
    -> Metal 4 when Whisky supplies D3DM_MTL4=1
```

The feature is D3D11-on-D3D12. It is not D3D12-on-D3D11.

## Non-negotiable invariants

- Use the exact `ID3D12Device` supplied by the application.
- Submit work through the supplied direct `ID3D12CommandQueue`.
- Do not create an independent WineD3D, DXVK, or D3D12 device as a fallback.
- Do not return success with incomplete or fabricated COM objects.
- Preserve COM identity and reference-counting rules.
- Initialize every requested output before returning failure.
- Propagate device removal and submission failures.
- Do not redistribute Apple D3DMetal or proprietary WDK headers.
- Preserve normal Apple D3D11 behavior outside `D3D11On12CreateDevice`.

## Architecture

### Why Microsoft's source is not sufficient by itself

Microsoft D3D11On12 is a D3D11 user-mode DDI driver. Its primary entry point is
`OpenAdapter_D3D11On12`; it is not the public Windows `d3d11.dll` runtime.

On Windows, the proprietary D3D11 core runtime:

1. validates public D3D11 API calls;
2. creates runtime handles and callback tables;
3. loads the D3D11On12 driver;
4. translates public COM calls into D3D11 DDI calls;
5. manages public COM objects, identity, and lifetimes.

Wine does not currently provide this DDI-host architecture. Its public D3D11
implementation calls WineD3D directly. Therefore, using Microsoft's mapping
layer requires a new host backend beneath Wine's D3D11 frontend.

DXVK cannot serve as the D3DMetal host unchanged. Its D3D11On12 path requires
vkd3d-proton's private `ID3D12DXVKInteropDevice` to import Vulkan objects.
D3DMetal does not expose that interface.

### Verified behavior of the Apple payload

GPTK 4.0 beta 2 was imported and deployed to the Whisky canary runtime. Whisky
correctly configured the tested D3DMetal bottle with:

- `D3DM_MTL4=1`
- `D3DM_FORCE_D3D11=1`
- builtin overrides for `d3d11`, `d3d12`, and `dxgi`
- production validation layers disabled

Apple's PE `d3d11.dll` exports exactly:

| Ordinal | Export |
| ---: | --- |
| 1 | `D3D11CreateDevice` |
| 2 | `D3D11CreateDeviceAndSwapChain` |
| 3 | `D3D11On12CreateDevice` |

Static inspection shows that Apple's `D3D11On12CreateDevice` immediately
returns `0x887a0004`, `DXGI_ERROR_UNSUPPORTED`. It does not invoke
`libd3dshared.dylib`.

The conformance probe could not run in the coding sandbox because Wine failed
to register its wineserver Mach port. This is an execution-environment
restriction rather than a missing payload or incorrect Whisky configuration.

## What exists today

### D3D11 router

`relay12-d3d11/d3d11shim.cpp` is a low-level C++17 PE router. It:

- preserves Apple's export names and ordinals at 1 to 3;
- forwards ordinary D3D11 creation to `d3d11mt.dll`;
- routes `D3D11On12CreateDevice` to `d3d11on12core.dll`;
- uses a versioned C ABI;
- clears On12 outputs before failure;
- returns `DXGI_ERROR_UNSUPPORTED` when no compatible core exists, and on the
  plain creation paths when Apple's forwarder is missing or incomplete, so
  every failure is a documented D3D11 return code;
- computes those results once at initialization, so the mapping has one
  definition;
- publishes `WineD3D11ShimGetStatus` at ordinal 4, so deployment can read the
  cause a documented `HRESULT` cannot carry;
- uses no exceptions or RTTI;
- is audited for accidental `libstdc++` and `libgcc_s` dependencies.

The original Apple forwarder must be renamed to `d3d11mt.dll` during
transactional deployment.

### Core boundary

`relay12-d3d11/d3d11on12core.cpp` exports:

- `WineD3D11On12GetABIVersion`
- `WineD3D11On12CreateDeviceV1`
- `WineD3D11On12GetInterface`, which publishes the size/versioned
  `WineD3D11On12Interface` function table

The current core validates:

- output initialization;
- non-null D3D12 device and queue inputs;
- exactly one queue for the initial supported configuration;
- `ID3D12Device` and `ID3D12CommandQueue` interfaces;
- direct command-queue type;
- queue/device COM identity;
- single-bit node masks;
- feature-level array consistency and D3D12 support.

Interface queries are propagated rather than flattened: a device object that is
not an `ID3D12Device`, or a queue object that is not an `ID3D12CommandQueue`,
yields that `QueryInterface` result instead of a generic `E_INVALIDARG`. A
success code returned with no interface breaks the COM contract, but this
boundary faces a proprietary payload, so it is treated as `E_NOINTERFACE`
instead of being dereferenced. Every interface acquisition in the core passes
through one `strictResult` funnel that applies that rule, and CI rejects a
`QueryInterface` or `GetDevice` call that bypasses it.

Device identity compares the two `ID3D12Device` pointers the core already
holds and consults `IUnknown` only when they differ, so a payload whose
`IUnknown` query returns a success code with no interface is still usable
while its typed pointers are stable, and an identity that cannot be
established is a failure rather than a match.

After validation, it intentionally returns `DXGI_ERROR_UNSUPPORTED`. The
success path must not be enabled until the DDI host produces genuine objects.

### Diagnostics

Neither module is a Wine builtin, so Wine's `ERR` and `TRACE` macros are not
available to them. Both report through the shared `wine_d3d11_diag` module,
which layers three sinks rather than trusting one:

1. `__wine_dbg_output`, resolved from `ntdll.dll` with `GetModuleHandleW` and
   `GetProcAddress` and never linked. Under Wine, `OutputDebugStringA` is
   delivered as a `DBG_PRINTEXCEPTION_C` raise, so an application with a
   debugger attached or a handler for that exception consumes the message
   first. This sink writes to Wine's stderr and cannot be intercepted that
   way.
2. `OutputDebugStringA`, which a winedbg session reads and which is the only
   sink on a real Windows host.
3. msvcrt's `stderr`, when the Wine sink was unavailable.

The export is Wine-internal and unversioned, so CI greps the pinned WineCX
`ntdll.spec` for it; dynamic resolution also keeps the import allowlist at
`kernel32` and `msvcrt`. Repeatable conditions report once per process, so an
application that probes `D3D11On12CreateDevice` in a loop cannot bury the
message it is meant to see.

The reported conditions are the ones that would otherwise fail silently:

- `d3d11mt.dll` missing, or missing an expected creation export, which means
  Apple's forwarder was not renamed correctly at deployment;
- `d3d11on12core.dll` present but publishing an incompatible interface table,
  which means a mismatched deployment;
- inputs accepted but no DDI host implemented, so the milestone's
  `DXGI_ERROR_UNSUPPORTED` is not mistaken for a driver or application bug;
- a supplied device or queue whose COM identity cannot be established, which
  is a payload contract violation rather than an application error.

Diagnostics are for a person reading a log. `WineD3D11ShimGetStatus` is the
machine-readable channel, and deployment gating must use that instead.

### Clean-room DDI declarations

`relay12-d3d11/ddi/wine_d3d11ddi.h` holds the clean-room rules and the
`WINE_DDI_ASSERT_*` size, alignment, and field-offset macros that every
declaration group must use. Six groups are declared:

1. Object handles (`D3D10DDI_HADAPTER`, `HRTADAPTER`, `HRESOURCE`, `HRTRESOURCE`);
2. Adapter function tables (`D3D10DDI_ADAPTERFUNCS`, `D3D10_2DDI_ADAPTERFUNCS`,
   `D3D10DDIARG_OPENADAPTER`);
3. Version negotiation arithmetic (`D3D11_DDI_MAJOR_VERSION` and composition macros);
4. Device creation (`D3D10DDIARG_CREATEDEVICE` at 88 bytes with embedded
   `DXGI_DDI_BASE_ARGS`, handles, `RetrieveSubObject`, and creation flags);
5. Core-layer device callbacks (`D3DWDDM2_6DDI_CORELAYER_DEVICECALLBACKS` at
   376 bytes, 47 slots over 46 distinct types, with
   `D3DWDDM2_2DDI_HRTCACHESESSION`);
6. Kernel device callbacks (`D3DDDI_DEVICECALLBACKS` at 528 bytes, 66 slots,
   with `D3DDDICB_ESCAPE`, `D3DDDICB_SYNCTOKEN` and the escape flags).

Group 5 is authored signature-complete rather than as bare slots, because it
is the one table the host fills and the driver calls: an unpromoted slot in a
driver-filled table is never invoked, but here the driver invokes the host on
its own schedule, and a wrong signature is a corrupted call frame. Two of the
47 are the exception. The structure page names
`PFND3DWDDM2_2DDI_SHADERCACHE_GET_VALUE_CB` and
`PFND3DWDDM2_6DDI_QUERY_SCANOUT_CAPS_CB` but links no page for either, and
both documentation surfaces return 404 for them, so they take a placeholder
function-pointer type that keeps their offsets exact and cannot be called
without an explicit cast.

One trap is recorded in the declarations rather than left to be discovered:
the D3D10-era refresh callbacks are documented as `(hRuntimeDevice, Count,
Base)` and the D3D11-era ones as `(hRuntimeDevice, Base, Count)`. Both
parameters are `UINT`, so no assertion and nothing about the ABI can catch a
host that implements one family with the other's order.

Group 6 takes the opposite approach to group 5, because the pinned driver
reads only three of its 66 slots: `pfnEscapeCb` in `Device::ReportError`, and
`pfnAcquireResourceCb` and `pfnReleaseResourceCb` in the present path. Those
three are promoted and the other 63 keep their published type names as
aliases of the undeclared-slot type, so the promoted set and the invoked set
are deliberately the same set. `pfnPresentCb` is a member of this table and is
*not* one of the three: the `pfnPresentCb` the driver calls belongs to the
DXGI table, and promoting on the strength of the name alone would put a
signature on the wrong slot.

The sync-token pair carries a constraint no offset assertion can express. The
driver stores `PFND3DDDI_SYNCTOKENCB D3DDDI_DEVICECALLBACKS::* const` and
binds it to one slot or the other, so the table must be a complete type in
C++ and both slots must have exactly that type rather than a merely
compatible function-pointer type. `tests/d3d11ddilayout.c` reproduces the
construct in its C++ arm.

The declarations are governed by strict verification gates:
- `tests/d3d11ddilayout.c` compiles under both C and C++ and confirms at run
  time that asserted offsets match actual compiler-generated structures;
- `scripts/check_ddi_header.py` validates provenance URL citations and dates
  on every declaration block and ensures no `#pragma pack` directives exist;
- `scripts/gen_ddi_layout.py --check` acts as an independent layout model,
  catching drift between specification walks and committed assertions.

Version negotiation is resolved without proprietary compile-time literals: the
runtime obtains supported-version words dynamically from `GetSupportedVersions`
and echoes the highest word's high 32 bits as `Interface`. Full layout details,
driver evidence, and union arm constraints are defined in `docs/CLEANROOM-DDI.md`.

## What remains

### 1. Strengthen the core ABI

The negotiated function table is in place; see the core boundary above. Two
things remain:

- Bump `WINE_D3D11ON12_ABI_VERSION` whenever table layout or field semantics
  change, keeping header offset assertions in sync.
- Replace lockstep size validation (`interfaceSize == sizeof(WineD3D11On12Interface)`)
  with forward-compatible negotiation (`interfaceSize >= offsetof(..., reserved)`)
  before either module ships independently.

### 2. Clean-room DDI declarations

The argument boundary structures and both host-filled callback tables are
complete. The remaining functional groups, governed by
`docs/CLEANROOM-DDI.md`, are:

- **Device function table**: `D3DWDDM2_6DDI_DEVICEFUNCS` (178 slots, layout first,
  gradual signature promotion);
- **Surface discovery**: Compiling the MIT tree against the clean-room header to
  produce a closed worklist of remaining resource, shader, and view structures;
- **DXGI DDI interop**: `DXGI_DDI_BASE_CALLBACKS` and `DXGI1_6_1_DDI_BASE_FUNCTIONS`.

### 3. Port D3D12TranslationLayer

- replace ATL and `CComPtr` dependencies;
- remove ETW and telemetry integration from this build;
- replace unsupported MSVC extensions and helper APIs;
- port DXBC parsing dependencies;
- eliminate MSVC runtime imports;
- retain upstream MIT notices and a reviewable patch series;
- build reproducibly with MinGW-w64 GCC C++17.

### 4. Port Microsoft D3D11On12

- compile against the clean-room DDI declarations;
- replace `_com_error` and other MSVC-only behavior;
- convert exceptions to `HRESULT` at the exported boundary;
- negotiate WDDM 2.7 as the highest advertised word at run time, matching the
  driver's internal assertion;
- disable unsupported display-kernel paths;
- retain the supplied device, queue, and node information.

### 5. Implement the Wine D3D11 DDI host

Refactor Wine's D3D11 frontend behind an internal backend operations table.
Keep WineD3D behavior unchanged and add a D3D11On12 backend that:

- calls `OpenAdapter_D3D11On12`;
- provides runtime adapter and device callbacks;
- allocates DDI private storage;
- translates public D3D11 calls into DDI calls;
- constructs `ID3D11Device` and `ID3D11DeviceContext`;
- exposes `IDXGIDevice` and `ID3D11On12Device` with correct COM identity;
- initially supports one node, one direct queue, and the immediate context.

Deferred contexts must return a truthful unsupported result until their full
recording and replay semantics are implemented.

### 6. Wrapped resources

Each wrapped resource must retain:

- the original `ID3D12Resource`;
- its owning D3D12 and D3D11On12 devices;\n- requested D3D11 interface and flag overrides;
- input and output D3D12 resource states;
- acquired or released ownership state;
- subresource state and in-flight lifetime data.

The ownership sequence is:

```text
D3D12-owned
    -> AcquireWrappedResources
    -> transition from declared input state
    -> D3D11-owned
    -> D3D11 commands
    -> ReleaseWrappedResources
    -> transition to declared output state
    -> flush/submit on the caller's queue
    -> D3D12-owned
```

Reject cross-device resources, double acquisition, unmatched release,
unsupported interfaces, and incompatible flags.

### 7. Queue synchronization

- serialize On12 submissions with use of the supplied queue;
- batch command lists and resource barriers;
- allocate monotonic fence values;
- recycle allocators only after fence completion;
- retain referenced resources until GPU completion;
- propagate device removal;
- wait during teardown when required;
- avoid CPU waits on ordinary submission paths.

### 8. Whisky deployment and capability gating

Deployment must be transactional:

1. validate the D3DMetal payload and runtime compatibility;
2. rename Apple's `d3d11.dll` to `d3d11mt.dll`;
3. install the router and compatible core;
4. verify hashes, ordinals, and Wine builtin markers;
5. run the end-to-end capability probe;
6. record `supportsD3D11On12` only after the probe passes, reading
   `WineD3D11ShimGetStatus` rather than the debug log;
7. restore the original payload atomically on any failure.

Initially require an explicit experimental setting. The implementation must
not infer support merely because `D3D11On12CreateDevice` is exported.

`D3DM_MTL4=1` remains controlled by Whisky. The core must not set or override
it. When enabled, On12-generated D3D12 work reaches Metal 4 because it uses the
caller's existing D3DMetal device.

### Core validation tests

`tests/d3d11on12coretest.c` links the core directly and drives it with mock
`ID3D12Device`, `ID3D12CommandQueue`, and plain `IUnknown` objects. The mock
vtables are designated initializers with unused slots left null, so a call the
core is not expected to make faults instead of passing unnoticed. CI links the
suite with the C driver, which also proves the core needs no C++ runtime, and
runs it under Wine.

Covered:

- the ABI version, and interface-table negotiation against an unsupported
  version or size;
- null and inconsistent arguments;
- non-D3D12 devices and queues;
- non-direct queues;
- a queue from another device;
- invalid node masks;
- unsupported feature levels, feature-level array forwarding, and propagated
  query failures;
- output initialization on every failure path;
- omitted optional outputs;
- objects that violate the COM contract by reporting success with no
  interface;
- a device whose `IUnknown` query is the violating one, both when its typed
  pointers still prove identity and when a foreign queue must be rejected
  without them;
- a propagated `GetDevice` failure;
- COM identity and reference-count balance across repeated calls.

These mocks need no GPU, no D3D12 runtime, and no Apple payload, so the suite
runs on any pull request. It is not a substitute for the graphics conformance
work below: it can only prove the boundary rejects what it must and never
returns success.

### Router fail-closed test

`tests/d3d11shimstatus.c` loads the built `d3d11shim.dll` in a prefix that has
no `d3d11mt.dll` and no `d3d11on12core.dll`, which is the deployment failure
the router must survive. It asserts that all three creation entry points
return `DXGI_ERROR_UNSUPPORTED` rather than an undocumented code, that
`D3D11On12CreateDevice` still initializes its outputs, and that
`WineD3D11ShimGetStatus` negotiates its size and version and reports the
absent modules. It also exercises the diagnostic sinks, since every one of
those paths reports.

### Conformance probe

`tests/d3d11on12probe.c` is the end-to-end probe, and cannot pass until the
DDI host exists. It exercises:

- D3D12 device and direct queue creation;
- `D3D11On12CreateDevice`;
- `ID3D11On12Device` discovery;
- wrapped BGRA render-target creation;
- acquire, clear, release, and flush;
- D3D12 fence completion.

CI cross-compiles and retains the probe as an artifact.

### Graphics conformance

- wrap buffers and textures;
- render-target clear and pixel readback;
- input/output state restoration;
- multiple subresources;
- D3D12 work before and after D3D11 work;
- fence completion on the original queue;
- repeated creation and destruction;
- concurrent submission;
- forced device removal;
- Direct2D and DirectWrite over a wrapped swap-chain buffer.

Successful API calls alone are insufficient. Tests must verify rendered data,

### Application validation

- Microsoft's D3D1211On12 sample;
- Chromium/CEF surfaces;
- Unity and Unreal initialization;
- video and UI middleware;
- representative D3D12 games;
- D3DMetal with Metal 4 both enabled and disabled.

## Policy

### Language and ABI

- Use low-level C++17 for the router and implementation.
- Export only `extern "C"` entry points.
- Do not allow C++ exceptions, C++ types, or allocator ownership across DLL
  boundaries.
- Compile the router with exceptions and RTTI disabled.
- Avoid static objects with nontrivial constructors and destructors.
- Use MinGW-w64 GCC for PE binaries; do not switch the Wine PE build to
  LLVM-MinGW.
- Prefer fixed-size, versioned ABI structures before the ABI becomes stable.
- The PE modules are `x86_64`, and the DDI layout contract is frozen for the
  Win64 `x86_64` ABI. Should an ARM target ever be in scope, the exposure is
  calling convention and ARM64EC thunking at the exported boundary, not
  structure packing; the DDI offsets for integer, enum, handle, and pointer
  fields are identical under the ARM64 Windows ABI.

C++26 is not the production baseline. Its MinGW/GCC support is less stable and
it provides no necessary feature that C++17 lacks for this component.

## Decisions and rejected alternatives

### `#pragma pack` on the DDI declarations — rejected

Proposed so GCC would mirror MSVC's packing on a future AArch64 target.

- The WDK DDI structures are not packed. MSVC x64 defaults to `/Zp8`, no field
  in this DDI has alignment above 8, and MinGW GCC already produces identical
  offsets. `pack(push, 1)` would break every layout and `pack(push, 8)` would
  change nothing, so the unresolved value is itself the hazard.
- The premise does not hold. ARM64 Windows also uses natural alignment with
  `/Zp8`; for structures of integers, enums, handles, and pointers the offsets
  are the same as x86_64. Packing is not what varies between those ABIs.
- It would defeat `WINE_DDI_ASSERT_ALIGN`, which exists to record the real
  alignment rather than force one.
- A stronger mitigation is already in place: `tests/d3d11ddilayout.c` and
  `scripts/gen_ddi_layout.py --check` verify all declared offsets at compile time,
  run time, and across independent models.

Instead, `wine_d3d11ddi.h` declares the frozen Win64 x86_64 contract,
prohibits `#pragma pack`, and `#error`s on any other target so the offsets
cannot be silently inherited by an ABI that has to re-derive them. CI rejects
`#pragma pack` under `relay12-d3d11/ddi`.

### `DXGI_ERROR_UNSUPPORTED` on the plain creation paths

The router previously returned `HRESULT_FROM_WIN32(ERROR_PROC_NOT_FOUND)`
(`0x8007007f`) when `d3d11mt.dll` was absent or incomplete. That code is not
in `D3D11CreateDevice`'s documented return set, so an application switching on
documented codes to orchestrate an API downgrade falls through to its default
branch.

The cost is that a broken deployment then looks exactly like a bottle without
D3D11 support. `WineD3D11ShimGetStatus` exists to carry the cause that a
documented `HRESULT` cannot, and deployment reads it. Ordinal 4 is a
deliberate addition beyond Apple's three exports, named so it cannot collide
with a future Apple export.

### Two-tier device identity

`IUnknown` is the canonical COM identity test, and using it alone was wrong
here. The payload can answer a query with `S_OK` and a null pointer, and two
such answers compared equal — so a queue belonging to a different device was
accepted, breaking the first non-negotiable invariant. Comparing the typed
`ID3D12Device` pointers first, and consulting `IUnknown` only when they
differ, rejects the foreign queue without rejecting a payload whose only
defect is that query.

### Negotiating WDDM 2.7 rather than 2.6 (superseding earlier 2.6 choice)

An earlier design targeted WDDM 2.6 on the assumption that negotiating 2.7
would require an unreleased `D3DWDDM2_7DDI_DEVICEFUNCS` table. Reading the
pinned driver revealed that WDDM 2.7 reuses the 2.6 table layout and that the
driver explicitly asserts `Interface == D3DWDDM2_7_DDI_INTERFACE_VERSION` in
`src/device.cpp`. Selecting 2.7 costs no additional declarations and satisfies
the driver's internal contract. `docs/CLEANROOM-DDI.md` § Version negotiation
records the full source analysis.

### Declaring 66 kernel callback slots where the surfaces say 65 and 66

The rendered syntax block for `D3DDDI_DEVICECALLBACKS` prints 66 members and
the markdown mirror 65. The difference is `pfnCreateNativeFenceCb`, a WDDM 3.1
addition the mirror has not caught up with. The dual-source rule forbids
resolving a disagreement by picking a surface, so this is resolved by taking
the union, which is not a pick.

The direction is what makes it safe. This structure is allocated by the host
and read by the driver, and both are compiled from this header, so the size is
not negotiated with anything outside the port. Over-declaring costs eight
bytes of zeroed, never-read storage; under-declaring is a heap overread the
first time a driver revision touches a slot past the end. The disagreement is
also confined to the tail: the three slots the pinned driver reads sit at
offsets 72, 432 and 440 under both surfaces, so nothing live can move.

Declaring 65 was rejected for the same reason it looks attractive — it reads
as respecting the frozen WDDM 2.7 target, but the published pages do not
version-gate per member, so "the members that exist at 2.7" is not something
either surface answers. Cutting at 65 would be a guess wearing a citation.

### An escape-flags type that deliberately does not use the published name

`D3DDDICB_ESCAPE.Flags` is declared as `WINE_D3D11DDI_ESCAPEFLAGS`, not
`D3DDDI_ESCAPEFLAGS`. The pinned WineCX already defines the published name, in
`include/d3dukmdt.h`, as the oldest variant: `HardwareAccess` and 31 reserved
bits. `DeviceStatusQuery` is the single bit the driver sets, and that variant
does not have it.

The host is Wine's D3D11 frontend and will include both headers, so the two
obvious options both fail: declaring our own under the published name is a
duplicate typedef, and deferring to WineCX's is a missing member. A distinct
name is neither, costs nothing at the ABI — the layout is identical and the
size is four bytes under every published variant — and the driver never
spells the type, only `EscapeCB.Flags.DeviceStatusQuery`.

Patching WineCX to add the missing bits was rejected as the wider blast
radius: the repository does carry Wine patches, but a patch to a shared
display header to satisfy one component is harder to justify and to rebase
than a private type name.

### Layered diagnostic sinks

Replacing `OutputDebugStringA` with `__wine_dbg_output` was proposed and is
half right. Wine delivers `OutputDebugStringA` as a `DBG_PRINTEXCEPTION_C`
raise, so an application with a debugger attached or a handler for that
exception consumes the message before Wine's output sees it. But it is also
the only sink on a real Windows host and the one a winedbg session reads, so
both are used, in order. The same failure mode appeared unlisted in the core,
which logged on every rejected call and would bury its own errors under an
application that probes in a loop; every repeatable condition now reports once
per process.
